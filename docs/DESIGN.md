# round-table（圆桌）— DSH 多方群聊协作插件 · 设计文档

> 工作名 `round-table`（可改）。目标：在 DeepSeek Harness Web GUI 内提供一个"AI 多方群聊与协同画布"，
> 把不同人设的 Agent 拉入同一研讨房间，互相讨论、交叉补充、质疑修正，最终产出综合性方案。
>
> 形态：官方 **bundle 插件**（Node half 编排 + 自渲染 client UI），参考 [whale-girl](https://github.com/vlln/whale-girl) 与
> [make-dsh-plugin skill](https://github.com/vlln/plugin-registry/blob/main/skills/make-dsh-plugin/SKILL.md)。

---

## 0. 术语表

| 术语 | 含义 |
|---|---|
| 房间（Room） | 一个独立的研讨空间，对应一个项目/议题；含成员（Agent 节点）、讨论历史、配置 |
| Agent 节点（Node） | 一个带独立 System Prompt / 性格 / 模型配置的 AI 角色实例（如"架构师"） |
| 发言模式（Mode） | 手动指定（@某 Agent）/ 全体研讨（全员依次）/ 接力链（Chain Reaction） |
| 轮次（Round） | 接力链/全体研讨中，全员按序各发言一次计为一轮 |
| 主持人 / 总结者（Summarizer） | 讨论结束后一键提炼最终方案的角色 |

## 1. 完整的用户操作流程（User Journey）

### 1.1 首次使用（Onboarding）

```
进入 GUI → 侧边栏出现「圆桌」入口 → 点击「新建房间」
  ├─ ① 命名房间 + 选择项目议题（如"XX 系统架构设计"）
  ├─ ② 创建 Agent 角色（由用户自己创建与命名）：填名称、头像色、System Prompt、性格参数
  │      创建后进入「角色库」，可复用于任意房间
  ├─ ③ 把角色拉入房间（可多选），设定讨论规则：默认模式（手动/全体/接力）、最大轮数上限
  └─ ④ 进入房间 → 看到空的时间线 + 成员已就位 → 输入首个议题，点击「全体研讨」或 @某 Agent
```

关键设计：**角色由用户自己创建与命名**（无内置模板库，避免角色人格被官方固化）；
一次创建、多房间复用；新建房间 30 秒内可开一场讨论。

### 1.2 日常讨论循环（核心路径）

```
打开房间（历史时间线完整保留）
  ├─ 输入议题 → 选择发言模式：
  │     · 手动：@架构师，直接点名（也可在正文中 @ 多人，按序回答）
  │     · 全体研讨：所有成员按设定顺序依次发言，每人为一轮
  │     · 接力链：A 回答完 → 系统自动把 A 的输出作为上下文传给 B → B 补充/质疑/修改
  ├─ 观察阶段：
  │     · 时间线实时滚动；思考中的 Agent 显示"正在思考…"气泡
  │     · 侧边栏轮次计数实时更新；随时可点「暂停」冻结讨论
  │     · 中途可：@ 指定某 Agent 插话、踢掉跑偏的成员、追加补充材料到上下文
  ├─ 控制阶段：
  │     · 达到最大轮数自动停止，或手动「结束讨论」
  └─ 产出阶段：
        · 点击「一键总结」→ 主持人/总结者 Agent 综合全部发言，产出确定性方案卡片
        · 卡片可：复制、导出 Markdown、存为"画布"（房间内的固定产出区）、@某 Agent 追问细化
```

### 1.3 事后与复用

- 房间历史永久保留，可随时重开续聊（上下文接续，Agent 记得上次结论）
- 可克隆房间（同阵容 + 新议题）复用角色配置
- 成员管理：随时拉入/踢出 Agent；改 System Prompt 后立即生效（后续发言按新设定）

### 1.4 异常与兜底

| 场景 | 行为 |
|---|---|
| 讨论跑偏/循环 | 全局「暂停」立即冻结；设轮次上限兜底；可「紧急插话」纠正方向 |
| Agent 调用失败/超时 | 该成员标记异常并跳过，其余继续；失败重试 1 次 |
| 用户离开页面 | **默认暂停**（可配置为后台继续）：回来时讨论停在原处，点「继续」恢复 |
| 成本失控 | 控制面板实时显示累计轮次与大致消耗；上限触发自动停止 |

### 2.1 总体布局（三栏结构，参照 Discord/Telegram + 会议工具）

### 2.2 时间线群聊区（核心交互面）

**消息气泡设计**：

- 每个 Agent 专属：头像（emoji/图片）、名称标签、角色标签、**专属色系**（气泡底色/名称颜色随成员固定，用户 0.5s 内识别发言主体）
- 系统消息（轮次开始/结束、暂停、踢人）居中灰底小字，不占视觉重心
- 用户消息靠左（或靠右，遵循主流聊天习惯），带"我"标记
- **流式输出**：Agent 发言打字机式实时渲染（与主会话体验一致）
- **思考指示**：成员发言前显示该成员头像 + "正在思考…"打字动效；思考中成员在侧边栏同步高亮

**消息操作**（hover 浮现）：

- 引用回复（点名让某 Agent 针对上一条发言回应——手动模式的核心入口）
- 复制 / 存为画布 / 标记（"已接受""有异议"轻量反馈，供总结者参考）
- 编辑删除（仅用户自己的消息）

**时间线导航**：轮次分隔线（"第 2 轮"锚点）+ 点击跳转；房间过长时按轮次折叠。

### 2.3 输入区与发言模式

```
[模式切换胶囊]：@指定 ｜ 全体研讨 ｜ 接力链        [发送]
[输入框：支持 @ 自动补全（弹成员列表，键盘上下选）]
[附加上下文：📎 引用某条历史消息 / 粘贴文本作为背景材料]
```

- **@指定**：输入 `@` 弹出成员补全；发送后仅被 @ 的 Agent 回答（多人则按序）
- **全体研讨**：全部在房间内的成员按设定顺序各答一次 = 一轮；对话内容随轮次累积
- **接力链**：A → 把 A 的完整输出作为上下文注入 → B 补充/质疑/修改 → C … 到链尾则回到 A（或结束），由轮次上限控制
- 三种模式可在讨论中途切换（暂停状态下切换生效）

### 2.4 全局控制面板（左栏/右栏）

| 控件 | 说明 |
|---|---|
| ⏸ 暂停 / ▶ 继续 | 全局冻结/恢复所有 Agent 发言（防死循环第一道闸） |
| 最大轮数 | 数字输入（1–20），达到即自动停止并提示"可一键总结" |
| 接力顺序 | 拖拽排序成员，定义链式顺序；可启用"回到链首"无限环 + 轮数上限 |
| 成员状态列表 | 每个成员：在线/思考中/空闲/异常；hover 显示其 System Prompt 摘要；右键菜单（改配置/踢出/置顶） |
| 累计统计 | 本轮已发言次数、预估消耗、耗时 |
| 一键总结 | 主按钮（讨论结束后高亮），触发总结者 Agent 提炼 |

### 2.5 一键总结与产出区

- 点击「一键总结」→ 右栏产出区出现"总结中…"→ 总结者 Agent 基于全部时间线提炼：
  - **确定性结论**（共识点 / 分歧点 / 待定项）
  - **推荐方案**（带理由，引用发言人）
  - **行动项**（谁做什么）
- 产出卡片：可复制 / 导出 Markdown / 重新总结（指定侧重点）/ 追问细化（@某 Agent 继续）
- 产出区（画布）常驻右栏，多张产出卡片可堆叠、置顶

### 2.6 交互细节补充

- 拖拽：成员头像可从右栏拖入/拖出房间（拉入=新成员；拖出=踢出，二次确认）
- 键盘快捷键：`Enter` 发送 / `Shift+Enter` 换行 / `@` 补全 / `Esc` 暂停
- 深色主题为主（对齐 DSH GUI）；气泡对比度满足可读性
- 房间内全部数据本地持久化（`~/.dsh/data/round-table/`），可导出房间 JSON 备份/分享

## 3. 多 Agent 讨论典型应用场景

### 3.1 场景 A：需求评审（新功能"支付网关接入"）

**房间配置**：产品经理（PM）、架构师（ARCH）、安全专家（SEC）、测试负责人（QA）

**讨论流程**（接力链模式，上限 3 轮）：

```
[用户]  @全体研讨：新需求——接入第三方支付网关，支持支付宝/微信，目标 2 周上线。
────────────────── 第 1 轮 ──────────────────
[PM]    澄清需求：分期支付是否支持？退款流程？目标量级？建议先定 MVP 边界。
[ARCH]  技术方案：网关抽象层 + 适配器模式；给出 3 种接入方案（直连/聚合支付/托管）与取舍。
[SEC]   质疑：直连方案 PCI-DSS 合规成本高；建议先做持卡人数据不落地的方案；列出风险清单。
[QA]    补充：建议分阶段验收：接口联调 → 沙箱全流程 → 灰度放量；给出测试矩阵草案。
────────────────── 第 2 轮（接力链）──────────────────
[ARCH]  采纳 SEC 意见，改为"凭据托管 + 不落卡号"方案；回应 QA：灰度放量周期需 PM 确认。
[PM]    拍板 MVP 范围：先支持支付宝单渠道 + 退款，微信二期；2 周工期改为 3 周。
[SEC]   补充合规检查项与上线安全 checklist。
[QA]    更新测试计划对齐新范围。
────────────────── 第 3 轮 ──────────────────
[ARCH]  汇总最终架构图要点；标注接口契约 v1 草案位置。
[PM]    输出最终需求确认单。
────────────────── 一键总结 ──────────────────
[总结者] 结论：MVP=单渠道+退款，3 周；方案=凭据托管+适配器；分歧=直连 vs 托管（已决议托管）；
        行动项：PM 出 PRD v1.1（D-1）、ARCH 出接口契约（D-2）、SEC 出合规 checklist（D-2）、QA 出测试计划（D-3）。
```

**设计亮点**：SEC 的质疑被下一轮 ARCH 主动采纳——体现"交叉补充 + 质疑修正"；总结者把讨论压缩为可执行产出。

### 3.2 场景 B：代码审查与修复（某模块性能问题）

**房间配置**：代码作者（DEV，持源码上下文）、代码审计员（REVIEW）、性能专家（PERF）、修复执行者（FIXER）

**讨论流程**（手动 + 接力混合）：

```
[用户]  把有问题的代码片段贴入上下文，@DEV：这段分页查询在大表上慢，怎么优化？
[DEV]   说明当前实现与取舍（曾用 N+1 查询改成了 join，但未做分页优化）。
[REVIEW] 指出：join 后未走覆盖索引；分页用 OFFSET 深翻页问题。
[用户]  @全体研讨：都说说优化方案。
[PERF]  方案：游标分页（keyset）+ 复合索引；给出预期收益量级。
[REVIEW] 补充：还有潜在锁竞争；建议 EXPLAIN 验证。
[DEV]   回应：接受游标分页；锁竞争场景确认存在，补充方案。
[FIXER] 产出最终 patch 草案（伪代码/描述），@PERF 确认边界条件。
[用户]  ⏸ 暂停 → 一键总结
[总结者] 共识：游标分页 + 复合索引；分歧：是否需要引入缓存（待压测后定）；
        行动项：FIXER 提交 patch、PERF 提供压测脚本、REVIEW 复查。
```

**设计亮点**：用户手动 @ 控制节奏，中途切换"全体研讨"拓宽视角；FIXER 收尾形成可落地产物。

### 3.3 场景 C：营销文案多稿 PK（轻量演示）

**房间配置**：文案策划（COPY）、增长专家（GROWTH）、法务审校（LEGAL）

```
[用户]   @全体研讨：为一款效率工具写 App Store 简介（中文），目标转化率。
[COPY]    3 版文案：理性功能向 / 场景共情向 / 社会认同向。
[GROWTH]  点评转化潜力，建议 A/B：首屏 3 秒抓人 + 评分证据。
[LEGAL]   提示"最佳效率工具"涉绝对化用语风险，建议改写。
[COPY]    根据意见出修订版（融合 GROWTH 的 A/B 建议与 LEGAL 的合规改写）。
[用户]   ⏸ → 一键总结
[总结者] 主推修订版文案 + 备选 A/B 方案 + 合规说明。
```

## 4. 技术落地要点（映射到 DSH bundle 插件架构）

> 依据已核实的 DSH 能力：`ctx.agents.create({model, provider, ...})` 可创建带独立
> System Prompt 的子 Agent；`ctx.sessions` 管理会话；`session/event`（turn/start、
> turn/end）与 `agent/created`/`agent/disposed` 可观察每个 Agent 的回合边沿；
> `ctx.jobs` 追踪任务。编排器基于这些事件驱动，与 whale-girl 的事件记账同构。

### 4.1 模块划分

```
round-table/
├── package.json            # dsh.bundle + dsh.client（官方 bundle 形态）
├── cordis.patch.yml        # insert 挂载自身
├── index.mjs               # Node half：房间/成员状态服务 + 编排器 + 路由
├── lib/
│   ├── client.js           # client bundle（构建产物，入库）
│   └── client/             # 时间线 UI 源码（纯 DOM 自渲染）
├── lib/src/                # 纯逻辑：编排状态机 / 路由规则 / 持久化 / 配置（零宿主依赖，可单测）
└── docs/DESIGN.md          # 本文档
```

### 4.2 Node half（编排核心）

| 职责 | 实现要点 |
|---|---|
| 房间/成员账本 | `~/.dsh/data/round-table/rooms.json`（原子写 + 防抖，同 whale-girl 持久化模式） |
| 角色库 | 用户自建角色（名称/色系/System Prompt/性格参数）持久化于账本，跨房间复用（决策 D5） |
| 多 Agent 实例 | 每成员 = 一个 `ctx.agents.create()` 子 Agent；**v1 统一模型**（沿用主会话 provider/model，决策 D1）。人设经「注入消息合成」实现：每次发言向成员 session 注入 角色卡（System Prompt）+ 房间上下文（近期讨论）+ 问题，不依赖 per-agent systemPrompt 专属 API |
| 消息路由 | 手动：向目标 Agent 的 session 注入用户消息并触发 turn；全体/接力：按顺序驱动，前序输出作为后序上下文 |
| 接力链状态机 | `turn/end` 事件驱动下一棒；维护轮次计数、链序、暂停/恢复、最大轮数（防死循环） |
| 事件订阅 | `session/event`（turn 边沿）、`agent/request-error`（失败跳过/重试）、`agent/created`（上线） |
| 页面离开 | 默认暂停 + 可配置后台继续（决策 D2）：client 发送 visibilitychange → 控制接口冻结 |
| HTTP API | `/round-table/*`：rooms / members / messages / control（暂停、轮次、总结）+ SSE 事件流；CSRF 校验 + body 上限 |
| 总结者 | 内置"主持人"角色（文本卡片式产出，决策 D3），对时间线做归纳，产出总结卡片 |

### 4.3 Client half（自渲染 UI）

- 纯 DOM 渲染三栏布局；时间线滚动虚拟化（长房间性能）
- SSE/轮询双通道同步状态（思考中/流式输出/轮次），参考 whale-girl 的 `/state` 轮询 + `/events` SSE 组合
- 成员色系、头像、状态在房间配置中定义，client 读取渲染
- 宿主 CSS 覆盖风险：关键样式 JS 内联（whale-girl 已验证的环境事实）

### 4.4 安全与成本控制

- 轮次上限（默认 5）硬性截断；暂停开关即时生效
- 每个 Agent 的 turn 都走既有凭据与限流；控制面板展示累计轮次与消耗估算
- 房间数据仅本地持久化；导出功能提供用户自控

### 4.5 开发与验证纪律（对齐 whale-girl 规范）

- 门禁 + 决策记录 + 生成物不手改（client.js 由脚本生成）
- 改动分层验证：纯逻辑单测 / Node half 重装 + 重启 web / client 改动刷新页面

## 5. 里程碑建议（Roadmap）

| 阶段 | 内容 | 验证 |
|---|---|---|
| MVP | 房间 CRUD + 用户自建角色库 + 手动 @ 发言 + 时间线 UI + 持久化 | 单房间、3 成员、手动模式跑通 |

## 5b. 工作区会话成员（混合房间，新功能）

除自建角色外，房间成员还可直接拉入**工作区既有对话框**（kind: 'session'），消除对话框之间的信息隔离：

- **成员两态并存**：`role`（自建角色）与 `session`（既有会话）可同处一室；session 成员以它自己的
  上下文/记忆/人设参与——不注入角色卡（会话本身即身份），只注入【圆桌讨论邀请】+ 房间上下文 + 议题
- **驱动对齐官方 session.prompt 模式**：`ctx.agents.get`（live）优先，冷会话 `ctx.agents.resume({resumeSessionId})`；
  `followup(buildUserMessage(...))` 队列注入（不打断该会话自身正在进行的回合）；`session/event` 的
  `turn/end` 回读 `assistant/message` 文本写入时间线并推进队列
- **会话枚举**：`GET /round-table/sessions`（来自 `ctx.sessions.list()`），client 提供"加入工作区对话框"选择
- **错误与兜底**：resume 失败/会话不存在 → 落失败消息跳过；LLM 错误 → turn/end reason=error 落失败消息；
  120s 超时强制结算；子 agent 专属会话（subagent ownership）→ 报错跳过
- **消息构造零 @deepseek-ai 依赖**：`buildUserMessage()` 手工构造（对齐 dsh-session 校验：id/role/source/content），
  插件不 import 官方包 → 任何安装方式（git 源/本地 link/符号链接）均可解析
